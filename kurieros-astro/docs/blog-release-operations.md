# Публикация блога: безопасный операционный порядок

## Что уже включено в коде

В репозитории подготовлены 100 материалов, но ни один из них не считается
опубликованным сам по себе. До фактического релиза будущие страницы:

- отсутствуют в маршрутах, sitemap, RSS и внутренних ссылках;
- не получают `datePublished` или искусственную историческую дату;
- не могут быть переданы в IndexNow или какой-либо API индексации.

Планировщик GitHub Actions запускается ежедневно в 09:05 по Москве, но курсор
разрешает только одну следующую статью и только при интервале не менее 48 часов.
Он никогда не догоняет пропущенные даты пачкой.

## Что нужно сделать перед первым автопостингом

1. Сначала вручную развернуть обычный технический релиз с выключенным
   планировщиком. Это создаст в production пустой
   `/api/blog-release-manifest.json`, с которым рабочий процесс сверяет
   локальный курсор.
2. Перед каждым материалом внести свежую запись в
   `src/data/blog-release-evidence.json`. Её `sourceIds` должны в точности
   совпадать с frontmatter статьи, `checkedAt` — быть не старше 30 дней, а
   `evidenceReference` — указывать, где редактор проверил первичный источник.
   При выпуске `checkedAt` записывается в неизменяемую release-запись: именно
   эта дата, а не дата черновика, показывается читателю как «Источники
   проверены».
3. Для материала с `researchGate: internal-dataset` в той же записи указать
   идентификатор набора, время снимка, SHA-256 снимка и методологию. Без этого
   такой материал остаётся заблокированным.
4. Оставить минимум 12 последовательных готовых материалов после следующего
   кандидата. Это буфер: если источники для одной статьи устарели, публикации
   останавливаются, а не перескакивают её.
5. Проверить план без записи файлов:

   ```bash
   BLOG_RELEASE_NOW='2026-08-03T09:05:00+03:00' \
   BLOG_SCHEDULE_ENABLED=true CONTENT_SCHEDULE_PAUSED=false \
   npm run blog:release -- plan
   ```

   Результат должен содержать ровно одного `eligible` кандидата и не содержать
   причин блокировки.

## Включение и аварийная остановка

По умолчанию автоматический релиз отключён. После успешного базового релиза и
редакционной подготовки владелец репозитория вручную задаёт переменные GitHub:

```text
BLOG_SCHEDULE_ENABLED=true
CONTENT_SCHEDULE_PAUSED=false
```

Для немедленной остановки достаточно установить
`CONTENT_SCHEDULE_PAUSED=true` (либо удалить/выключить
`BLOG_SCHEDULE_ENABLED`). Уже опубликованные URL при этом не меняются.

Для автоматического запуска нужен
`TIMEWEB_DEPLOY_METHOD=ssh-archive`. Только этот путь умеет поставить
финальный timestamp в staging непосредственно перед публикацией. При любой
другой конфигурации ежедневный job завершается без кандидата и без деплоя;
archive и FTP остаются только ручными диагностическими путями. Старый GitHub Pages workflow отключён,
поэтому он не может обойти курсор или отправить sitemap пачкой в IndexNow.

Планировщик перед подготовкой кандидата сверяет production-манифест по HTTPS.
Обычный запуск принимает только совпадающее состояние: неожиданный production
релиз впереди ledger останавливает процесс до ручной проверки. После успешного
запланированного деплоя отдельный шаг может записать ровно один релиз только
если production-запись совпадает с неизменяемой reservation того же job. Это
защита от двойной публикации, отката и подмены публичного manifest.

## Индексация после фактического релиза

После успешного деплоя статья попадает в sitemap, RSS, внутренние ссылки и
публичный release manifest. Этого достаточно для обычного обхода Google и
Яндекса. Не используем Google Indexing API для редакционных статей: он
предназначен только для `JobPosting` и `BroadcastEvent`.

Опционально можно включить ровно одно уведомление IndexNow для только что
развёрнутого URL. Перед этим надо создать секрет GitHub `INDEXNOW_KEY`,
проверить, что файл владения с этим ключом находится в корне `dist`, и лишь
затем установить:

```text
BLOG_INDEXNOW_ENABLED=true
```

Уведомление не является обещанием индексации и не отправляет будущие URL или
пакет из 100 адресов. После релиза редактор вручную проверяет URL в Google
Search Console и Яндекс Вебмастере; отправка на переобход допустима только для
уже публичной страницы.

## Даты и правки

Временный кандидат получает только служебный timestamp для сборки; при
автоматическом SSH-релизе Timeweb проставляет финальные `releasedAt` и
`firstPublishedAt` в staging непосредственно перед переносом на публичную
поверхность. Этот момент затем подтверждается production manifest и только
после этого фиксируется в git. Заднее число для нового текста не используется.
Если нужно обновить уже опубликованный материал, сохраняется его первая дата,
увеличивается revision, фиксируется `modifiedAt`, и изменение проходит обычную
проверку источников.

## Полезные команды

```bash
# Проверить весь корпус без публикации.
npm run check:blog-content

# Удалить локальный временный кандидат после тестовой сборки.
npm run blog:release -- discard-candidate

# Проверить финальный HTML, sitemap и допустимое изменение SEO-поверхности.
npm run build
npm run seo:audit
npm run test:dist
```

Ни одна из этих команд не публикует сайт и не отправляет данные во внешние
поисковые сервисы.
