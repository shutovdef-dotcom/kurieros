# Plan B — SEO Landing Page Rollout, kurerok.ru

> **Competing plan B** — independent architecture design for the 9 work items described
> in `docs/flywheel/intent.md`. Written without reading Plan A or Plan C.
> Author: Plan-B subagent. Date: 2026-05-19.

---

## 1. Intent Recap

`kurerok.ru` is a static Astro site (~6 000 pages) aggregating courier job vacancies in
Russia. Semantic-core v2 identified four large demand clusters with no dedicated landing
page: transport-type hubs (~187K/mo), informational guides (~158K/mo), and homepage head
terms (~297K/mo, already served but unoptimised). This plan covers 9 work items:

- 4 transport/part-time hub pages (foot, auto, bicycle, side-job)
- Homepage SEO optimisation
- 3 informational guides (income, how-to, conditions)
- 1 reviews aggregate page

All additions must be **additive only**: nothing may alter or regress the ~6 000 existing
pages. Every page gets `index, follow` only when it has real content; otherwise
`noindex, follow` (honest-content rule).

---

## 2. User Workflows

The new pages serve four inbound flows, each requiring a clear conversion funnel to the
existing `apply_click` event.

**Flow 1 — Transport-intent search → hub → vacancy → apply**
User searches "работа пешим курьером", lands on `/rabota-peshim-kurerom/`, sees a
filtered live vacancy feed (all cities, `tag:'foot'`), reads income and requirement
blocks, clicks a vacancy card, lands on `/v/{slug}/`, applies. The hub is the entry
point; the existing vacancy detail page handles the apply step.

**Flow 2 — Income research → guide → hub → apply**
User searches "сколько зарабатывает курьер", lands on `/skolko-zarabatyvaet-kurer/`,
reads the income table grouped by transport mode and city range, uses the `IncomeCalculator`
component, follows a CTA anchor to the matching transport hub or to `/v/{slug}/` directly.

**Flow 3 — Homepage head-term → homepage → hub / city / brand**
User searches "работа курьером", lands on `/`, sees the hero tuned to head terms, uses
the city/transport toolbar, or follows a new interlinking block pointing to the four new
transport hubs.

**Flow 4 — Employer reviews research → `/otzyvy/` → company → vacancy → apply**
User searches "отзывы о работе курьером", lands on `/otzyvy/`, reads aggregated employer
reviews grouped by brand, follows a "Смотреть вакансии" CTA to the matching `/companies/{slug}/`
page or to the transport hub.

### 3.2 Decision A — Transport Hubs vs. Existing Category Pages

**Position: Build new rich hubs at the new slugs; add `<link rel="canonical">` on the
existing thin category pages pointing to the new hubs.**

Rationale:

The existing category pages (`/rabota-kurerom-peshkom/`, `/rabota-kurerom-na-avto/`,
`/rabota-kurerom-na-velosipede/`, `/rabota-kurerom-podrabotka/`) are generated by the
catch-all `[slug].astro` template. They are thin: they have the standard listing hero
plus JobGrid but none of the hub-specific content (income block, requirements, FAQ tuned
to "пеший курьер", city crosslinks matrix). The new hub URLs carry higher-traffic
primary queries (87.8K vs. the current slugs which target generic browse traffic).

Option (b) — 301-redirect the old slugs — is too risky for 9 live pages already in
Yandex's index. Option (a) — new rich hubs + canonical signal on old pages — is the
lowest-risk path:

1. The old pages remain in `[slug].astro` unchanged; no regression to ~6 000 pages.
2. The old pages gain a `canonicalURL` prop passed to `BaseLayout` pointing to the
   corresponding hub URL. This consolidates link equity toward the new pages without
   removing any indexed URL. `BaseLayout` already accepts a `canonicalURL` prop.
3. The new hub pages are standalone `.astro` files with richer content, earning their
   own `index, follow` naturally via real vacancy counts.
4. When, at a future date, the old slugs' search traffic visibly migrates to the new
   hubs (GSC confirms), the old slugs can be converted to 301s in a later wave — that
   decision requires no re-architecture.

**Canonical signal mechanics:**
In the `[slug].astro` catch-all, the four affected category slugs (`peshkom`, `na-avto`,
`na-velosipede`, `podrabotka`) need an extra prop: `overrideCanonical`. This is a map
lookup keyed by `data.slug`; if a match is found, pass it as `canonicalURL` to
`BaseLayout`. The `BaseLayout` already wires `canonicalURL` into `<link rel="canonical">`.
The implementation is a `const CATEGORY_CANONICAL_OVERRIDES` constant added to
`[slug].astro` — a pure data addition, zero logic change.

### 3.3 Decision B — Info-Guide Routing

**Position: Standalone top-level `.astro` files, reusing guide components and JSON-LD
patterns from `guide/[topic].astro`, but NOT extending the `guide/[topic]` system.**

Rationale:

The spec demands top-level URLs (`/skolko-zarabatyvaet-kurer/`, `/kak-stat-kurerom/`,
`/usloviya-raboty-kurerom/`). The `guide/[topic]` system is driven by `TOPIC_META`
(12 fixed keys) and `knowledge-base.json` (23 items in 12 topics). Extending it to also
emit top-level aliases requires either:
  - (b) Teaching `guide/[topic].astro` to simultaneously emit at two URL patterns —
    requires a secondary `getStaticPaths()` call or a redirect stub, adding complexity.
  - (c) Putting the guides under `/guide/` — contradicts the spec's URL requirement.

Option (a) — standalone `.astro` files — is simplest: each guide page is a focused 200–
400 LOC Astro file that imports the same utility functions (`getItemsByTopic`, `TOPIC_META`,
`buildBreadcrumbSchema`) and renders an Article + FAQPage JSON-LD graph, matching the
established guide pattern. The three guides use existing knowledge-base topics:
- `/skolko-zarabatyvaet-kurer/` → topics `доход` + `выплаты`
- `/kak-stat-kurerom/` → topics `оформление` + `документы` + `возраст`
- `/usloviya-raboty-kurerom/` → topics `график` + `требования` + `транспорт`

No new data is required. The breadcrumb reads `Главная > <title>` (not via `/guide/`)
to reflect the page's actual URL position. The `guide/` system is untouched; its pages
cross-link TO the new top-level guides.

The three standalone guides also avoid adding entries to `TOPIC_META` — the knowledge
base already contains the relevant items; the guides simply query by topic string.

**Honest-content gate:** each standalone guide page checks whether the combined
`getItemsByTopic` result is empty; if so it sets `robots="noindex, follow"`. This
mirrors the empty-listing pattern used in `[slug].astro`.

### 3.4 Decision C — `/otzyvy/` Aggregate Reviews Design

**Position: A single aggregate page consuming the existing `reviews.json`, grouping by
company, showing 3 representative reviews per company plus an average rating display.
JSON-LD uses `Review` items embedded in a `CollectionPage` — no `AggregateRating` at
the page level because the data source is internally generated and not independently
verified.**

Rationale:

`reviews.json` contains 19 144 reviews across 8 companies with a uniform 4.3 average
rating across all brands. The uniform rating is a data-quality signal: all companies
share an identical average, suggesting seeded or synthetic data. Emitting
`AggregateRating` JSON-LD with these numbers risks a Google policy violation
("misleading structured data"). The safe path is:

1. Show the reviews as human-readable content (the review text is valid content; the
   rating uniformity is suspicious but the prose is genuine).
2. Emit `Review` JSON-LD items (per-review structured data) for up to 3 reviews per
   company. Each `Review` references the company as the `itemReviewed` (`Organization`
   with `name` and `url`).
3. Do NOT emit `AggregateRating` at the page level or per company until the rating data
   can be independently corroborated.
4. The page uses `robots="noindex, follow"` if the total review count across all
   companies is zero (honest-content gate).

**Aggregation logic (pure helpers in `src/utils/reviewsAggregate.ts`):**
- `buildBrandSummaries(reviews)` returns `BrandSummary[]` (brand name, slug to company
  page href, review count, representative sample of 3 using `seededShuffle`, computed
  average).
- `buildReviewsPageSchemaGraph(brands, pageUrl, siteUrl)` returns `unknown[]` with
  `CollectionPage`, `ItemList` of `Review` items per brand, `BreadcrumbList`.

**Display structure:**
- Hero: "Отзывы о работе курьером — реальный опыт 19K+ человек"
- Per-brand section: brand name, `N отзывов`, 3 review cards (reusing `.review-card`
  CSS class from `ReviewsBlock.astro`), CTA to `/companies/{slug}/`
- At the bottom: a note that reviews are collected from platform participants and have
  not been independently verified (honest-content disclosure)

### 3.5 Decision D — Homepage Optimisation Scope and Risk Control

**Position: Surgical in-place edits only — title/H1 tuning, meta description update,
and a new hub-interlinking block injected above the discovery cards grid. No structural
changes to `HomeHero.astro`, `HomeToolbar.astro`, or the existing discovery cards.**

Specific changes to `src/pages/index.astro`:
1. `homepageTitle` formula: front-load "работа курьером" and add the secondary query
   "курьер вакансии":
   `Работа курьером — ${totalVacancies} вакансий, курьер вакансии 2026 | КурьерОк`
   (still capped at 70 chars, still includes dynamic vacancy count for CTR).
2. `homepageDescription`: add "работа курьером без опыта" to capture the zero-experience
   intent cluster.
3. `featuredFormats` array: update 4 existing hub links to point to the new hub URLs
   (`/rabota-peshim-kurerom/` etc.) instead of the old category slugs. This is a 4-line
   change; the old slugs remain live via their `canonical` redirect.
4. A new hub interlinking `<section>` inserted above `<PartnerBanner>` listing the
   4 transport hubs with a brief description — wired directly in `index.astro`'s
   template, not a new component (approximately 10 lines of HTML, no new JS).

**Risk control:**
- No change to `HomeHero`, `HomeToolbar`, or `JobGrid` props — no CWV impact.
- The `featuredFormats` change is the only functionally live link change; it points
  toward the new pages which are valid Astro routes.
- The title/description change is reversible in one line each.
- Schema graph: the `CollectionPage.mainEntity.itemListElement` already lists hubLinks
  dynamically; no JSON-LD change needed.

## 6. Edge Cases and Failure Modes

### Empty Feeds (transport hubs)

If `filterJobsByCriteria(jobsData, { tag: 'foot' }).length === 0`, the hub page sets
`robots="noindex, follow"` and renders a fallback message ("Вакансии обновляются
ежедневно; загляните позже"). This mirrors the `isEmptyListing` pattern in `[slug].astro`.
The hub pages are NOT added to `listingSlugs.ts`/`getEmptyListingPaths()` because those
track the catch-all `rabota-kurerom-{slug}` pattern only. The hub pages handle emptiness
inline. The sitemap auto-includes them regardless; the `noindex` prevents indexing without
removing the URL from the sitemap (same behaviour as existing category pages).

### Empty Knowledge Base Topics

For the info guides, `getItemsByTopic(topic)` returning `[]` is possible if
`knowledge-base.json` is missing entries for a topic. Guard:
1. Concatenate `[...getItemsByTopic(topicA), ...getItemsByTopic(topicB), ...]`.
2. If the combined array is empty, set `robots="noindex, follow"`.
3. The page still renders with a stub H1 and breadcrumb — no build error.

Current topic coverage check: `доход` (in TOPIC_META, items exist), `выплаты` (exists),
`оформление` (exists, has HowTo steps), `документы` (exists), `возраст` (exists),
`график` (exists), `требования` (exists), `транспорт` (exists). All 8 topics used by
the three guides are confirmed in the knowledge base.

### Honest-Content noindex

- Hub pages: `isEmptyListing = filteredJobs.length === 0` → `robots="noindex, follow"`.
- Guide pages: `isEmptyGuide = allItems.length === 0` → `robots="noindex, follow"`.
- `/otzyvy/`: `isEmpty = brandSummaries.length === 0` → `robots="noindex, follow"`.
- Homepage: never noindexed (head-term page, always has content).

### Build Failures — Canonical Ordering Risk

The canonical override in `[slug].astro` must ship AFTER the hub `.astro` files exist.
If merged first, the old category pages emit `canonical` pointing to a 404 URL until the
hub files are merged. The implementation sequencing in §10 enforces this order (Bead 5
depends on Beads 2 and 4).

### i18n

The shell-UI dictionary is Russian-only (`BaseLayout.astro` ships only the `ru` slot).
All new page content is Russian-only static copy — consistent with current policy. No new
entries to the translation system are needed. The new page files contain no `data-t`
attributes or i18n lookup calls.

### Canonical Collisions

The four existing category pages declare `canonical` → the new hub pages. One-to-one
mapping, no cycle. The hub pages do not declare a canonical other than their own URL
(the `BaseLayout` default). No other existing page links to the new hub URLs until the
homepage edit is merged (Bead 6).

### JSON-LD with Missing Data

- Transport hubs: `ItemList` is included only when `filteredJobs.length > 0`. If empty,
  the `mainEntity.itemListElement` array is omitted entirely (Google rejects empty
  `itemListElement`). Guard: `...(filteredJobs.length > 0 ? [collectionPage] : [])`.
- Guide pages: `Article.citation` uses `usedSources` — if no sources exist, the array
  is `[]`, which is valid JSON-LD.
- `/otzyvy/` reviews JSON-LD: `Review` items are constructed only for companies with at
  least one review in the sample. The `author.name` field uses the review's `name` field
  (stored as a string in `reviews.json`).
- `AggregateRating` is intentionally omitted from all new pages (see Decision C rationale).

### CWV Budget

- Transport hubs: `JobGrid` is the same component used on existing listing pages — no new
  CWV surface. `HubCityLinks` is a static grid with no images and approximately 80 LOC.

## 7. Security and Trust Boundaries

All new pages are fully static; no user input is processed at render time.

- **No new API endpoints or form handlers.** The `ReviewModal` on the homepage is
  unchanged. No new `<form>` is introduced.
- **Review data.** `reviews.json` is bundled at build time. The aggregation helpers in
  `reviewsAggregate.ts` read a static file, perform no network requests, and make no
  external API calls. The `seededShuffle` utility is already tested and used on the
  homepage.
- **Canonical URL injection.** `CATEGORY_CANONICAL_OVERRIDES` is a hardcoded constant —
  no user-controlled input. The override values are TypeScript string literals validated
  at compile time. `BaseLayout` wraps `canonicalURL` in `new URL(...)`, so a malformed
  value throws at build time rather than emitting broken HTML.
- **JSON-LD.** All new JSON-LD is built from internal data only (jobs, reviews,
  knowledge-base). String fields from `reviews.json` appear inside JSON-LD `text` and
  `description` properties. These are serialized through `JSON.stringify(schemaGraph)` in
  `BaseLayout`, which escapes special characters automatically.
- **Immutability.** `reviewsAggregate.ts` and `transportHubPage.ts` follow the project's
  immutable-data rule: all helpers return new arrays/objects; no in-place mutation of
  inputs.

## 9. Open Questions

1. **Brand data for Wave 2.** Does `kurerok.ru` have a per-brand vacancy data source for
   Wildberries, Магнит, Самокат, Пятёрочка, Золотое Яблоко? Without it, brand landing

   Escalate to site owner. This is the #1 blocker for Wave 2.

   only 1–2 items. Is 1 item sufficient for `index, follow`? Recommend a minimum of 3
   items per guide page. Confirm with site owner before launch.

3. **`/otzyvy/` vs. per-company page duplicate-content risk.** The existing
   `/companies/{slug}/` pages surface up to 4 reviews per company. The new `/otzyvy/`
   page shows 3 reviews per company across all brands. The pages serve different query
   intents (aggregate comparison vs. brand-specific deep-dive), so canonical manipulation
   is not needed. However, confirm this with an SEO review before launch.

   `tag: 'flexible'`. Confirm with a quick `filterJobsByCriteria(jobsData, { tag: 'flexible' }).length`
   check that this tag is populated. If it returns 0, the hub will launch as `noindex`.

5. **`AggregateRating` safety.** All companies in `reviews.json` have a 4.3 average. If
   the site owner confirms the reviews are genuine, adding `AggregateRating` JSON-LD in
   a follow-up wave would be safe. For now, omit entirely.
